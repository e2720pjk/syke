04 / Findings before merge

REAL ISSUES, NOT THEORETICAL NOISE
P1 · FIX

v2 fork lineage is documented but not selected

adapter-opencode.md 說要保留 parent_id、fork_session_id、fork_boundary，但 v2/mixed metadata SQL 只選 title、time、agent、model。照 guide 執行會遺失 subagent/fork context。

最小修正： v2 projection 加入三個 fork 欄位；mixed CTE 的 legacy branch 用 NULL 對齊欄位，測試 metadata query 的實際輸出。
DECISION · LEGACY

Legacy recency policy contradicts itself

文件指出 legacy time_updated migration 後不再前進，但 legacy-only query 仍只按它排序；mixed CTE 也不會從 message/part 取得新的 activity。這不是 v2 parser bug，而是 compatibility policy 的缺口。

選項： 若保留 legacy（建議，因 live DB 實際混存），加入 message/part recency；若只要 v2，則明確移除 legacy reconstruction，不要半保留。
P2 · TEST

Reference helper reads until EOF

測試 helper 用 while True 讀完整頁，與 seed 宣稱的 bounded budget 不完全一致。這是測試品質問題，不是 production runtime regression；可用固定 page budget 簡化。

NO BLOCK

06 / Minimum merge strategy

PRESERVE · MERGE · PROVE
1

SAVE WIP

目前 index 空、4 個檔案仍在 working tree。不要在此狀態直接 merge。

git diff --binary > /tmp/opencode-v2.patch
2

NEW WORKTREE

從 current HEAD 建立一次性 integration branch，保持正式分支可回復。

git worktree add ../opencode-v2-pi-test -b test/opencode-v2-pi HEAD
3

CARRY WIP

在 test branch 套用 patch，做 temporary WIP commit，再合併 Pi feature。

git apply /tmp/opencode-v2.patch
git merge --no-ff feat/pi-session-ingestion
4

RESOLVE POLICY

文件只合併必要內容；catalog/setup/tests 保留雙方語意；先修 fork lineage。

git status
git add <resolved-files>
5

PROVE BOTH

先 deterministic suite，再用兩個 source 做一次真正 synthesis。

uv run python -m pytest -q
uv run syke sync --source opencode --source pi

Why legacy support is a compatibility decision, not automatic scope creep

OpenCode v2 and legacy tables can coexist in the same live database. The current observed database contains both session_v2/session_message and session/message/part. Therefore mixed-schema reads and stable-ID precedence serve an existing-user migration boundary. They are not required to introduce v2, but deleting them would be a product behavior change. Keep them if backward compatibility is part of the product contract; isolate them in a named compatibility commit if the goal is a strictly minimal v2 delta.

What is intentionally not recommended
  • Do not run git merge feat/pi-session-ingestion while the current working tree is dirty.
  • Do not resolve setup_support.py or catalog.py with a blanket “ours” or “theirs”; both source contracts must remain.
  • Do not use the current global syke as proof that the worktree code ran; its uv direct URL currently points to another checkout.
  • Do not treat the passing reference parser as a production OpenCode parser; this project intentionally remains LLM-first.
Bottom line: merge for integration testing, not for blind adoption. Standalone artifact · no external assets · no legacy report dependency
